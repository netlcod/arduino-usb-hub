# Расследование: G305 — порядок X/Y в репортах за USB Host Shield

Статус: **в работе** (Фаза 0).

## Контекст и установленные факты

Приёмник Logitech G305 (VID `046D`, PID `C53F`) декларирует в дескрипторе
репорта порядок полей Y → X, но за USB Host Shield фактические данные идут
X → Y. Сведённая таблица доказательств:

| Условие | Декларация | Факт на проводе | Источник доказательства |
|---------|-----------|-----------------|-------------------------|
| Ресивер → ПК напрямую | Y@DataIndex16, X@17 | Y first | Дамп USB Tree Viewer (`InputCaps`: строки Usage 0x0031/DI16 перед 0x0030/DI17) + корректное поведение курсора под mouhid.sys (декодирование строго по дескриптору) |
| Ресивер → host shield | тот же дескриптор | **X first** | Эксперимент: прошивка без калибровки даёт чистый своп осей (вправо→вниз и т.д.) |

Вывод: один и тот же дескриптор, разный фактический порядок байтов у разных
хостов. Windows не «распознаёт» порядок — он декодирует строго по
дескриптору; расхождение означает, что данные от ресивера зависят от хоста.

Текущее решение: source-only калибровка `wire_order` в
`profiles/sources/g305.json` (X=16, Y=17; `data_index` не трогается),
пересоздаётся вручную после re-clone (см. Gotchas в AGENTS.md).

Цель расследования: найти фактор, вызывающий расхождение, и при возможности
заменить калибровку на устранение причины.

## Гипотезы

| # | Фактор | Гипотеза |
|---|--------|----------|
| F1 | Вендорный интерфейс / handshake | Ресивер держит legacy-раскладку, пока хост не проинициализировал композит полностью (вендорный интерфейс `MI_03`, usage page `0xFFBC`); G HUB/драйвер делает это на ПК |
| F2 | Активация всех интерфейсов | Роутинг/формат репортов меняется только при конфигурации всех HID-интерфейсов композита |
| F3 | BOOT vs REPORT протокол | Разница в `SET_PROTOCOL` меняет формат данных |
| F4 | SetIdle / тайминги энумерации | Маловероятно, но проверка дешёвая |

Что известно о стеках:
- Щит (`hidboot.h:462-474`, `HIDBoot(&Usb, true)`): setConf →
  `SetProtocol(mouse_iface, REPORT)` → `SetIdle(0,0)` → чтение report
  descriptor'а. Активирован **только мышиный интерфейс**.
- ПК: биндятся все 5 коллекций композита (keyboard 13B, consumer 5B,
  system 2B, vendor FFBC 2B, mouse 9B), драйверы ОС + возможно Logitech-софт.

## Фаза 0 — эталонные снятия

### A. Снятие за щитом (CDC-enabled сборка)

Дамп сырых репортов требует Serial (CDC), но свежее ядро не содержит
сгенерированных заголовков. Порядок — через рабочий пайплайн с временным
отключением одного флага:

```powershell
# 1. Обычный прогон: гарантирует сгенерированные заголовки в Mouse/src
arduino-hub flash --device g305 --target generic_5btn --sketch examples/mouse/mouse.ino --port COM6

# 2. Временно включить CDC: удалить "-DCDC_DISABLED" из boards.txt
#    (arduino-cli-data\packages\arduino\hardware\avr\<ver>\boards.txt)

# 3. examples/mouse/hidmouserptparser.h: #define HUB_DEBUG_DUMP 1

# 4. Сборка/загрузка/монитор напрямую, минуя patch:
.build\tools\arduino-cli.exe compile --config-file arduino-cli.yaml --fqbn arduino:avr:leonardo examples\mouse
.build\tools\arduino-cli.exe upload   --config-file arduino-cli.yaml -p COM6 --fqbn arduino:avr:leonardo examples\mouse  # reset-танец
.build\tools\arduino-cli.exe monitor  --config-file arduino-cli.yaml -p COM6 --config baudrate=115200
```

Процедура движений: только вправо (5 c) → пауза → только вверх (5 c) →
колесо. Записать hex-строки `RPT ...` (лимит 20 репортов за запуск).
Ожидание по текущей модели: дельта в байтах [3..4] при движении вправо.

Восстановление после экспериментов: обычный `arduino-hub flash`
(idемпотентно вернёт `-DCDC_DISABLED` и пересоберёт всё).

### B. Снятие ПК-стороны (Wireshark + USBPcap)

1. Запустить захват на интерфейсе USBPcap соответствующего хаба **до**
   подключения ресивера (чтобы попала энумерация).
2. Подключить ресивер → определить адрес устройства → фильтр
   `usb.device_address == N`.
3. Те же движения. Сохранить `profiles/sources/reports/g305-pc-direct.pcapng`.

### C. Что извлекаем

- Interrupt IN данные (`usb.capdata`) во время движений → какие байты
  меняются (ожидание: [3..4] = Y first на ПК-стороне).
- Все control-transfers энумерации: `SET_PROTOCOL` (bRequest 0x0B, wValue),
  `SET_IDLE` (0x0A), запросы дескрипторов/строк, **всё адресованное
  не-мышиным интерфейсам**, особенно вендорному `0xFFBC`.

Критерий перехода к Фазе 1: найдены конкретные транзакции, которые делает
ПК и не делает щит (или подтверждено их отсутствие — это тоже результат,
отпадают F2/F4-часть гипотез).

## Фаза 1 — изоляция фактора

Каждый шаг = отдельный тестовый скетч (`examples/xy_probe/`, основной
пример не трогаем). Критерий успеха каждого E: изменилась ли позиция дельты
X в дампе Фазы 0-A (стала ли Y-first).

| # | Эксперимент | Проверяет |
|---|-------------|-----------|
| E1 | `HIDBoot(&Usb, false)` — boot-протокол | F3: сменится ли формат/порядок |
| E2 | Убрать `SetIdle` | F4 |
| E3 | Активировать все HID-интерфейсы композита (клавиатура/consumer/system) | F2 |
| E4 | Повторить вендорные транзакции из Фазы 0-C (если есть) | F1 |

Порядок определяется результатами Фазы 0 (сначала ближайший к найденной
разнице).

## Фаза 2 — выводы

- **Фактор найден** → фикс на стороне скетча/либы (например, воспроизвести
  handshake), убрать `wire_order`-калибровку из `profiles/sources/g305.json`,
  обновить AGENTS.md/README/test-комментарии.
- **Не найден** → зафиксировать заключение «ресивер хост-зависим, причина не
  установлена»; калибровка остаётся как легитимный quirk (аналог таблиц
  hid-quirks ядра Linux).
